# Forecast 수집·표시 점검 (2026-09-11)

## 결론

로컬 DB 1,376건 / Target 8개를 점검했다. 현재 수집기는 응답 항목 전체를 `raw_json`으로 저장한다. 기존 컬럼만 표시한 UI 때문에 계약방법·규격·수량·담당부서 등이 가려져 있었다. 발주계획 통합번호와 순번은 별도 컬럼에도 이미 보존되어 있다. 수집기를 전면 재작성해야 한다는 결론은 현재 자료로 뒷받침되지 않는다.

## 반영

검색 목록과 Live 응답의 금액을 합계발주금액으로 변경했다. 상세에 식별자·업무구분·계약방법·품명·용도·규격·수량/단위·합계발주금액·담당부서/담당자/전화·비고·공고번호·원문 링크를 추가했다. 기존 발주도급금액은 별도 명칭으로 유지한다. 원문에 없는 금액은 0으로 만들어 내지 않는다.

서버 조회 시 원문을 해석하므로 기존 전체 데이터와 앞으로 수집되는 데이터에 동일하게 적용된다. DB 원본 수정이나 네트워크 재수집이 필요 없다. 공고번호는 원문 그대로 표시하며 자동 단계 연결 기능을 구현한 것은 아니다.

## Backfill 판정과 남은 범위

- 저장된 원문의 표시 복구: 가능하며 이번 수정으로 적용. 별도 DB backfill 불필요.
- 과거 누락 행 재수집: 현재 collector는 명시적 날짜 범위를 7일씩 나누어 페이지를 순회하고 source_key로 upsert하므로 재사용 가능. 다만 실제 API의 과거 제공 범위·호출한도·응답 완전성은 이번에 실호출 검증하지 않았다. 대량 backfill은 실행하지 않았다.
- 원문에도 없는 국제입찰 여부, 수의계약사유, 사전규격번호: 현재 저장 응답에서 확인되지 않는다. 다른 조회 오퍼레이션/상세 또는 계약과정통합공개서비스의 응답과 권한을 검증한 뒤 별도 보강해야 한다. 협정 여부를 국제입찰 여부로 대신 표시하지 않는다.
- 수집 완전성: 로컬 공개일 범위는 2025-01-20~2026-09-11이다. Target 8개와 최근 검사 구간 중심 수집이므로 전국/전체 기간 대비 누락률은 로컬 DB만으로 산정할 수 없다. 동일 Target·동일 기간 API 총건수와 식별자 대조가 필요하다.

공식 서비스 설명은 예산액·발주예정시기·발주방법·주소·연락처 제공을 명시한다. 또한 발주계획 없이 후속 사전규격/입찰/계약이 존재할 수 있다고 설명한다: https://www.data.go.kr/data/15129462/openapi.do

금액 필드 명칭은 기존 mona-live에 보존된 `temp/order-plan-response-schema.json`의 sumOrderAmt 설명(합계발주금액, 원화 원)과 실제 저장 응답을 대조했다.
